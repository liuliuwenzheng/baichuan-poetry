# 数据质量发现清单

做这个项目的过程，一半时间花在**发现上游数据到底错在哪**。全部结论都有可复现的
查询支撑，不是猜测。原文改正前后均可回滚（`data/fix_log*.json`）。

---

## 一、朝代字段系统性错误：25 万首被标成「唐」

**现象**

| | 修复前 | 修复后 |
|---|---|---|
| 宋 | 21,091 | **271,806** |
| 唐 | 337,874 | 87,154 |

`authors` 表的朝代是对的（陆游=宋、朱熹=宋），但 `poems` 表**几乎全写成唐**。

**根因**

上游 `chinese-poetry` 仓库的 `全唐诗/` 目录里，实际混着 `authors.song.json` 和
`poet.song.*.json`（**510 个宋诗文件 vs 116 个唐诗文件**）。导入程序按目录名
把整批宋诗当唐诗灌进库里。

**修法**

用上游原始清单重判作者朝代：

- `全唐诗/authors.song.json` 等 → 8,934 位宋诗人
- 唐清单 3,675 位
- 两份都有（239 位）→ 跨代诗人，**不动**

再让诗跟随作者，但**只修「诗中标为唐」这一种已知默认错误**。

**为什么不能无脑跟随作者**——三个差点改错的地方：

| 迁移 | 数量 | 真相 |
|---|---|---|
| 元 → 宋 | 1,943 | 全是**无名氏**：元曲佚名作品会被改成宋 |
| 五代 → 唐 | 482 | 全是**花间集词人**（温庭筠/韦庄/李煜）——作者表那个"唐"才是错的 |
| → 其他 | 600 | **佚名**：会把《诗经》的先秦标注毁成"其他" |

结论：**只改有权威清单背书的，宁可少改不可错改。**

## 二、简繁匹配失效：繁体库漏掉 19,707 首

**现象**：简体库归位了 25 万首，繁体库只归位了一部分——繁体库「清单外」作者 1,688 位 vs 简体 453 位。

**根因**：繁体库里的作者名是 `陸遊`、`楊萬裏`，而权威清单里是 `陆游`、`杨万里`。
两边直接用字符串比较，整批对不上。

**修法**：两边都归一化到简体再比（`zhconv.convert(s, 'zh-hans')`）。
清单外作者从 1,688 → 376。

## 三、南唐二主误判：李煜一直挂着「唐」

**现象**：李煜（93 首）作者朝代 = 唐，应该 = 五代。

**根因**：李煜**同时**出现在宋清单和唐清单里（南唐跨代）。原逻辑把"两表都有"
一律当歧义跳过，而这个"歧义"判断**排在**南唐规则之前，所以李煜根本没被处理。

**修法**：判定顺序改成「确定 > 一般」——南唐二主是史有定论的事实，优先级最高。
李煜、李璟 → 五代。

> 教训：**规则冲突时，确定的知识必须排在统计性的启发式之前。**
> 顺序错了，再对的规则也执行不到。

## 四、简繁转换污染：「海内存知己」→「海记忆体知己」

**现象**：`#24669` 王勃《送杜少府之任蜀州》正文变成
「海**记忆体**知己，天涯若比邻」。

**根因（v0.2.0 已更正）**：这一条我一开始判错了。

我最初以为是 palemoky 的流水线用 OpenCC `s2twp`（简→**台湾正体**，带短语表）
把「海**内存**知己」按「内存 → 記憶體」的词条吃掉了。

**但重新从 MIT 原始数据构建时发现：这个错字在 chinese-poetry 的上游源码里就有**——
`御定全唐詩/json/056.json` 字面写着「海記憶體知己」。也就是说它不是转换事故，
而是**上游数据自带的错字**（像「內存→記憶體」这类机翻用词替换的残留），
palemoky 的库只是把这个错继承了下来。

**教训**：根因要一直挖到**最上游的那份数据**，不能停在自己这一层的工具链上。
我当时只做了「简体表里有错→繁体表里也有→所以是转换造成的」这个推断，
跳过了「上游原文可能本来就错」这一步。

**修法（v0.2.0）**：加**勘误表**（`ERRATA`，`tools/ingest.py`），逐条登记
`错误原文 → 正确原文`，在简繁转换**之前**应用，两种字形同时受益。

```python
ERRATA = [("海記憶體知己", "海內存知己"), ("海记忆体知己", "海内存知己")]
```

**这才是生成繁体不能偷懒用 `s2twp` 的真正理由**——不是因为它是本次事故的元凶，
而是因为它会把现代词汇一并替换，**正是上游那类错字的成因**。本项目用
`zh-hans`/`zh-hant` 字符级直转，不带短语表。

**顺便纠正一个误判**：我最初把「手机/网络/系统/程序」也当成脏数据，查证后
全是合法的古典用法——

- 手机：「敏手机心颇自安」（机心、机敏）
- 网络：「连网络朱绳」
- 程序：「广平程序字古伦」（人名，姓程名序）

**只有「海记忆体」一条是真脏数据。** 用现代词表扫古典文本，误报率极高。

## 四之二、全宋诗整批挂在「唐」下（v0.2.0 从源头消除）

**现象**：宋诗只有 21,091 首，而「唐」有 337,874 首，比例荒谬。

**根因**：上游目录 `全唐诗/` 里同时躺着

- `poet.tang.*.json` **59 个**（真·全唐诗）
- `poet.song.*.json` **256 个**（全宋诗！）
- `authors.tang.json` 与 `authors.song.json`

目录名叫「全唐诗」，内容里宋诗是唐诗的 4 倍多。任何「遍历该目录、按目录名定朝代」
的导入器，都会把 25 万首宋诗标成唐——palemoky 的流水线正是这么做的。

**修法对比**：

| | v0.1.0 | **v0.2.0** |
|---|---|---|
| 做法 | 导入后跑 `fix_data.py`，用上游作者清单重判 25 万首 | **导入时按文件名判朝代** |
| 代价 | 需要保守传播规则、繁简归一、优先级排序，且差点误伤元曲/诗经 | 无需修补，不存在这个错 |

**教训**：**能被文件名确定的事实，不要留给事后统计推断。**
一个字段的语义如果在源头就摆着，任何「启发式还原」都是在给未来的自己挖坑。

## 六、名字这道墙：库里有「陶潜」，读者搜「陶渊明」

陶渊明在数据里的名字是**陶潜**（本名）。按"查不到"下结论就错了——
第一轮我报告"陶渊明仍缺"，实际是搜错了名字。

同类：郑板桥=郑燮、李后主=李煜、苏东坡=苏轼、唐伯虎=唐寅。

**这不是数据错误，是可用性缺陷**：一个数据源再好，用习惯叫法搜不到就等于没有。
→ `author_aliases` 表（33 组，241 条），建索引时简繁归一化，
`陸遊` 和 `陆游` 都能命中同一个人。

## 七、朝代被写进体裁名：体裁轴与朝代轴被压成一维（v0.3.0 修）

**症状不是「数据错了」，而是「模型错了」** —— 这是最难发现的一类，因为每条数据单看都"合理"。

上游 `poetry_types` 表把**【朝代】和【体裁】两个正交维度压进了同一个字段**：

| id | 名称 | category | 实际挂着的朝代 |
|---|---|---|---|
| 11–14 | 五言绝句 / 七言绝句 / 五言律诗 / 七言律诗 | **"唐诗"** | 全部朝代（七言绝句：宋 87,173 / 唐 12,459） |
| 20 | **宋词** | "宋词" | 宋 21,017 **+ 清 257** |
| 21 | 五代词 | "词" | 五代 425（分类还跟 20 不一致） |

三个可验证的后果：

1. **纳兰性德的清词被标成「宋词」**。257 首清代的词，挂在名叫"宋词"的体裁下。
2. **查「所有词」必须硬编码** `type_id IN (20, 21)`。来一个新朝代（比如明词）就崩。
3. **「七言绝句」的 category 说它是唐诗**，可它挂着 8.7 万首宋诗。

修法：拆出独立的体裁轴 `genres_*`（1诗 2词 3曲 4诗经 5楚辞 6论语 7蒙学 8四书五经 9其他），
`poems.genre_id` 挂上去；体裁名里**一律不带朝代**（10「唐诗」→ 10「诗」，20「宋词」→ 20「词」，
21「五代词」并入 20）。朝代只归 `dynasty_id`。

修完的效果（`genre_id × dynasty_id` 组合查出来的）：

| | 唐 | 宋 | 清 |
|---|---|---|---|
| **诗** | 88,507 | 366,750 | 109,576 |
| **词** | — | 23,362 | **8,579** |
| **曲** | — | — | —（元 10,891） |

并把「体裁名里不得出现朝代名」写成自动断言（`tools/verify.py` C 段）——
以后谁再写「宋词」这种名字，校验立刻红。

## 八、简繁两表 id 错位：换个文字版本就返回另一首诗（v0.3.0 修）

**这是接口层的致命伤，而且不看不知道。**

简繁两表本该「同一 id = 同一首诗」，但 v0.2.0 的繁体表做了两件多余的事：
自己又去重一遍（`if hant_hash not in seen_hant`）、自己又开了一个 id 计数器（`next_pid_h`）。
于是繁体侧每丢一行，两套 id 就错开一位，**越往后错得越多**：

| id | 简体表 | 繁体表 | |
|---|---|---|---|
| 11 | 《饮马长城窟行》 | 《飲馬長城窟行》 | ✅ 同一首（只是文字不同） |
| 200000 | 《题赵苇江雁荡图》 | 《題趙葦江雁蕩圖》 | ✅ 同一首 |
| 400000 | 《荒村》 | 《心雲詩爲羅宗仲先生賦》 | ❌ **不同的诗** |
| 960000 | 《秋日书怀…其二》 | 《陽春門堤上》 | ❌ **不同的诗** |

差 25,294 行 = 25,294 个错位的 id。任何 `GET /poems/400000?script=hant` 都会返回另一首诗。

修法：**诗的身份只由简体表定义**（去重只发生在简体侧）；繁体表是它的
**同 id 逐条镜像**，不设独立计数器、不做二次去重。代价是繁体文本里可能出现字面重复
（两首不同的诗转成繁体后字面相同）—— 这是对的，把这两首诗合并才是真丢数据。

修完：两表 **993,753 / 993,753**，行数恒等，同 id 元数据 0 不符。
`tools/verify.py` E 段自动守这条不变量。

```bash
# 朝代分布
sqlite3 data/baichuan.db "SELECT d.name, count(*) FROM poems_zh_hans p
  JOIN dynasties_zh_hans d ON p.dynasty_id=d.id GROUP BY 1 ORDER BY 2 DESC"

# 关键作者守护（李白杜甫白居易必须还是唐，陆游苏轼必须是宋）

  JOIN dynasties_zh_hans d ON a.dynasty_id=d.id LEFT JOIN poems_zh_hans p ON p.author_id=a.id
  WHERE a.name IN ('李白','杜甫','白居易','陆游','苏轼','李煜','陶潜') GROUP BY a.id"

# 污染残留（应为 0）
sqlite3 data/baichuan.db "SELECT count(*) FROM poems_zh_hans WHERE content LIKE '%记忆体%'"

# 孤儿引用（应为 0）
sqlite3 data/baichuan.db "SELECT count(*) FROM poems_zh_hans p
  LEFT JOIN authors_zh_hans a ON p.author_id=a.id WHERE a.id IS NULL"
```
